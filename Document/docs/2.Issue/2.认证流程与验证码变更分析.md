### 3.5 请求时序与 queryString 的「两种形态」（HAR 实证）

同一条 queryString 在流程里被以**三种编码层数**使用，弄错任意一处都会表现成
「账号密码错误」这类误导性报错。约定如下（`requests` 提交 `data=` 时会再编码一层，
所以代码里传的值要比线上字节「少一层」，只有拼在 URL 上的例外）：

| 位置 | 浏览器线上字节 | 代码里应传 |
|---|---|---|
| `GET index.jsp?<qs>` | `wlanuserip=9660...&mac=...`（原始形态，`&` 是真分隔符） | **原始形态** |
| `POST InterFace.do?method=pageInfo` | `queryString=wlanuserip%3D9660...%26mac%3D...`（单层） | **原始形态** |
| `POST/GET InterFace.do?method=getServices&queryString=<qs>` | URL 上单层 `%3D`/`%26` | **编码形态** |
| `POST userV2.do?method=getServices` 的 `search` | `%3Fwlanuserip%3D...`（`?` + 单层） | `"?" + 原始形态` |
| `POST InterFace.do?method=login` 的 `queryString` | `wlanuserip%253D9660...`（**双层**） | **编码形态** |
| 同上 `service` | 有线 `%25E6%25A0%25A1...`（双层），无线 `iSMU` | 有线 `%E6%A0%A1%E5%9B%AD%E7%BD%91`，无线 `iSMU` |

其中「原始形态」= `location.search.substring(1)`，也就是网关重定向地址里的样子；
「编码形态」= 对它做一次 `encodeURIComponent`（`&`→`%26`、`=`→`%3D`）。
探测抓回来的 queryString 是**编码形态**，取字段（如 `mac`）前必须先 `unquote`。

浏览器的完整时序（网口，HAR 共 30 条请求，摘出关键几跳）：

```
1. GET  index.jsp?<原始queryString>              建会话（JSESSIONID）
2. POST InterFace.do?method=pageInfo             ← queryString 单层
3. POST InterFace.do?method=getServices&queryString=<编码>   绑定本会话可用服务
4. POST InterFace.do?method=getOnlineUserInfo    userIndex=（空，探测已有会话）
5. GET  validcode?rnd=<随机数>                    取验证码图
6. POST userV2.do?method=getServices             username + search="?"+原始 ← 返回「校园网」
7. POST InterFace.do?method=login                带 validcode + RSA 密文
8. GET  success.jsp?userIndex=...
9. POST InterFace.do?method=portalAuthSuccessConfig
10. POST InterFace.do?method=getOnlineUserInfo   userIndex=<上一步返回值> → "success"
```

> 第 3 / 4 跳原先被漏掉。第 3 跳（`getServices`）与「服务」直接相关，
> 已在登录流程里补上；第 4 跳 `getOnlineUserInfo(userIndex="")` 暂未复现，未见必要性。

另：`service`（接入服务）在页面上来自隐藏域 `net_access_type.value`，
而它由 Cookie `EPORTAL_COOKIE_SERVER` 或服务端 `$defaultValue` 决定 ——
本校页面里 `$defaultService = '请选择服务'`、**`$defaultValue = ''`**，
即首次访问时该隐藏域是**空**，浏览器会提交 `service=`（空），由门户走系统默认服务。
而服务的合法取值只有两种：有线 `校园网`、无线 `iSMU`。

## 四、密码加密机制

`login_bch.js` 的加密逻辑：

```javascript
var encrypt = document.getElementById("passwordEncrypt").value;  // 来自 pageInfo
var macString = getQueryStringByName("mac");
if (isNull(macString)) macString = "111111111";

if ("true" == encrypt) {
    if (password.length < 150) {
        var passwordMac = password + ">" + macString;    // 明文 + ">" + mac
        password = encryptedPassword(passwordMac);        // 内部会先反转，再 RSA 加密
    }
} else {
    if (password.length > 150) encrypt = "true";          // 已加密的长串则自动置 true
}
```

⚠️ **`encryptedPassword` 会把明文整个反转**，这一步极易漏掉：

```javascript
// interface/index_files/js/AuthInterFace.js（唯一的定义处）
function encryptedPassword(password){
    var passwordEncode = password.split("").reverse().join("");
    ...
    RSAUtils.encryptedString(key, passwordEncode);  // 这里要对字符串进行反转，否则解密的密码是反的
}
```

- `security.js` 的 `RSAUtils.encryptedString` **自己不做反转**，反转发生在调用侧；
- `login_bch.js` 里只有 3 次**调用**，没有定义；`index.jsp` 里 `encryptedPassword` 出现 0 次
  ⇒ 生效的一定是 `AuthInterFace.js` 那一份，反转**必然发生**；
- 因此真正的加密明文是 **`reverse(password + ">" + mac)`**。

**加密方案已实机复现验证**（下载门户 `interface/index_files/js/security.js` 逐字节比对后修正）：

- 算法：`RSA`，modulus 1024 bit，`e = 0x10001`
- 填充：**不是 PKCS#1 v1.5**。门户用的是 David Shapiro（ohdave）**RSAUtils** 库的自定义填充：
  1. 把字符串按 **UTF-16 码元**展开（`charCodeAt` 语义）
  2. 末尾补 `0` 直到长度为 `chunkSize` 的整数倍
  3. 每 `chunkSize` 个码元打包成 `chunkSize / 2` 个 **16 位小端字**，拼成大整数 `m`
  4. `c = m^e mod n`，输出十六进制（每个 16 位字固定 4 位，块间用**空格**连接）
- **`chunkSize = 2 * biHighIndex(modulus) = 126`**（对 1024 位模数），**不是 128**
- 明文：**`reverse(password + ">" + mac)`**（反转的是 UTF-16 码元序列）
- 输出：块内 256 位小写十六进制
- 与 HAR 中密码长度（256 hex）**完全一致** ✅
- 提交时 `passwordEncrypt=true`

> 纯 Python 实现见 `src/shmtu_auth/src/core/portal_crypto.py`。
> oracle 脚本 `tools/portal_crypto_oracle.js` 会**同时加载** `security.js` 与
> `AuthInterFace.js`，直接调用门户自己的 `encryptedPassword()`（含反转）。
> 单测：`PyTest/test_portal_crypto.py`、`PyTest/test_portal_crypto_parity.py`。
>
> ⚠️ **教训**：最初只用 `security.js` 自建一个「拼接后直接 RSA」的包装当 oracle，
> 结果漏掉反转 —— 而且填充算法照样逐字节自洽，测试全绿，于是把错误结论写进了实现：
> 门户解出来的密码是反的，任何密码都被判「用户不存在或者密码错误!」。
> 生成期望值必须调用**门户自己的函数**，而不是自己重写一层调用。

> 服务端对已加密密码（`passwordEncrypt=true`）可正常处理（实测返回"认证失败"而非格式错误）。

### 5.3 `service` 是怎么定的（下拉框机制，已完全查清）

登录页的 `service` 是**下拉框**，值由服务端下发，不能写死。整条链路：

**① 提交值来自隐藏域 `net_access_type`，且被编码两次**

`login_bch.js`：

```javascript
var service = "";
if (document.getElementById("net_access_type")) {
    service = encodeURIComponent(encodeURIComponent(document.getElementById("net_access_type").value));
}
```

**② 隐藏域由下拉项的 `selectService()` 第一个参数写入**

```javascript
function selectService(serviceName, serviceShowName, serviceNum){
    $("#selectDisname").html(serviceShowName);          // 展示名
    ...
    $("#net_access_type").attr("value", serviceName);   // ← 提交用的原始值
}
```

**③ 真实值由 `userV2.do?method=getServices` 给出**

输入学号后门户会 POST `userV2.do?method=getServices`（`username=<学号>&search=?<queryString>`），
**返回的是原始服务名，且随网络环境自动变化**（实机验证）：

| queryString 来源 | 接口返回 | ×2 编码后提交 | HAR 实际提交 |
|---|---|---|---|
| 网口/有线 | `校园网` | `%E6%A0%A1%E5%9B%AD%E7%BD%91` | ✅ 一致 |
| ISMU/无线 | `iSMU` | `iSMU` | ✅ 一致 |

**④ Python 侧只需要编码一次**

因为 `requests` 的 `data=` 还会再编码一次，所以把 `userV2` 的返回值做**一次**
`urllib.parse.quote(..., safe="")` 即可，线上字节与浏览器完全一致
（`urlencode` 结果实测等于 HAR 里的 `service=%25E6%25A0%25A1%25E5%259B%25AD%25E7%25BD%2591`）。

> ⚠️ **不要直接把 `userV2` 的返回值当 `service` 提交**：它是**展示名**（中文原文），
> 少编码一层就与服务端期望的 `%E6%A0%A1...` 不匹配。

> ⚠️ `InterFace.do?method=getServices` 在本校（`typeflag=true`，后台统一配置）未登录时
> 只下发 **`[-1-1]系统默认服务[-1-1]` 占位项**，拿不到真实服务列表 —— 必须走 `userV2`。

**⑤ 最终方案：不猜，两个都试**

`userV2` 看起来能自动告诉我们该用哪个，但它的前提是「当前网络类型判断是对的」。
在 **Docker / 容器 / 网关代拨** 场景下这个前提经常不成立：拿到的是宿主机或上一跳的
网络类型，于是 `service` 就选错了，登录必然失败。

因此最终实现**不按网络类型二选一**，而是把两个候选都试一遍：

```
候选顺序：[校园网(有线), iSMU(无线)]
  └─ 逐个跑完整流程（取验证码 → 识别 → login）
      ├─ 成功 → 记住这个类型（仅内存），返回
      ├─ 验证码类错误 → 立即返回（换接入类型也没用）
      └─ 其它失败   → 换下一个候选
```

- 代价：选错时多一轮请求（一次取图 + 一次 POST），可以忽略
- 收益：有线 / 无线 / 类型判断错误全都能自愈
- 唯一例外：`SHMTU_AUTH_PORTAL_SERVICE` 显式配置时**只试它**，方便排查
- 本进程上次成功的类型会排到最前面（内存记忆，不落盘），常驻容器从第二轮起一次命中

实现见 `ShmtuNetAuthCore._portal_service_candidates()` + `_portal_login_once()`，
`encode_service_param()` 负责那一次编码。`query_account_service()` /
`query_services()` 保留下来做日志排查，不再参与选择。

### 5.4 响应编码陷阱（曾导致验证码重试完全失效）

门户 `pageInfo` / `login` / `getServices` 返回 **`Content-Type: text/html`（不带 charset）**，
`requests` 会退回 **ISO-8859-1**：

```
res.text        →  {"message":"éªè¯ç éè¯¯."}
UTF-8 解码      →  {"message":"验证码错误."}
```

后果：`is_valid_code_error()` 认不出"验证码错误"，**重试与快速失败逻辑全部静默失效**，
错误提示也是乱码。修复方式是读 `res.content` 后**强制 UTF-8 优先解码**
（见 `EPortalClient._response_text`）。

### 5.5 `ServiceType` 补充

`ServiceType` 原本只有 `EDU = "%E6%A0%A1%E5%9B%AD%E7%BD%91"`（校园网），
现已补上 `ISMU = "iSMU"`。注意这两个常量存的都是**编码一次后的形态**，
正好等于 `quote("校园网")` / `quote("iSMU")`。

## 六、改造要点（已实施）

认证流程由「3 步」改为「5 步」（另加登录前的 `getServices` 绑定，共 6 跳）：

```
① GET  index.jsp?<queryString>          建立会话，拿 JSESSIONID
② POST InterFace.do?method=pageInfo      取 validCodeUrl / passwordEncrypt / RSA 公钥
③ GET  validcode?rnd=<rand>              下载验证码图片
④ 识别验证码  （OCR / 人工 / 第三方）
⑤ POST InterFace.do?method=login         带 validcode + RSA 密文密码
```

要点：

1. **必须持有同一个 `requests.Session`**（JSESSIONID 绑定验证码）。
2. **验证码一次性**：每次登录失败后，用响应里的新 `validCodeUrl` 重新取图识别，不能复用。
3. **RSA 公钥每次从 `pageInfo` 现取**，不要写死（会轮换）。
4. **`service` 不要写死，也不要猜**：两个候选（有线 `校园网` / 无线 `iSMU`）依次都试，
   配置项 `SHMTU_AUTH_PORTAL_SERVICE` 可显式定死一个。详见 5.3。
5. **验证码识别**方案（按体验排序）：
   - a) **自动 OCR**：4 位纯数字、无干扰线（80×30 橙色数字）。实测 `ddddocr` 5/5 全对，
     单张耗时 ~30ms，是首选
   - b) **交互式输入**：GUI 弹窗显示验证码图片请用户手输（OCR 失败时兜底）
   - c) **失败重试**：验证码一次性，失败后用新的 `validCodeUrl` 重取新图再试。
     **OCR 识别不出来也算一次可重试的失败**（无 GUI 的环境没有弹窗兜底，
     一次识别失败就整轮放弃太脆弱），默认重试 6 次
6. **失败响应要识别**：`"验证码错误."` → 重取验证码重试；`"认证失败"` → 账号密码/接入
   类型问题，不要原地重试（但可以换另一种 `service` 再试，见 5.3⑤）。
   **注意响应要按 UTF-8 解码**（见 5.4），否则这一步会静默失效。

## 七、复现/验证命令

> 三种形态别写错（完整契约见 §3.5）：`<raw_qs>` = `wlanuserip=…&mac=…`（原始形态），
> `<enc_qs>` = `wlanuserip%3D…%26mac%3D…`（编码形态）。
> 现成的脚本比手工 curl 省事：抓 queryString 用 `diagnose_portal.py`，
> 跑完整流程用 `test_auth_cli.py`（`--manual` 手输验证码）。

```bash
# 1) 取会话 —— 必须用「原始形态」拼在 URL 上
curl -sk -c cj.txt -o index.html \
  "https://ismu.shmtu.edu.cn:8443/eportal/index.jsp?<raw_qs>"

# 2) 取 pageInfo（看 validCodeUrl 是否非空）—— body 用「原始形态」
curl -sk -b cj.txt -c cj.txt -X POST \
  "https://ismu.shmtu.edu.cn:8443/eportal/InterFace.do?method=pageInfo" \
  --data-urlencode "queryString=<raw_qs>"

# 2.5) 绑定本会话可用服务（浏览器在 pageInfo 之后会调）—— URL 上用「编码形态」
curl -sk -b cj.txt -c cj.txt \
  "https://ismu.shmtu.edu.cn:8443/eportal/InterFace.do?method=getServices&queryString=<enc_qs>"

# 3) 取验证码图片（每次 GET 都是新图）
curl -sk -b cj.txt -c cj.txt -o vcode.png \
  "https://ismu.shmtu.edu.cn:8443/eportal/validcode?rnd=0.123456"

# 4) 提交（需先识别 vcode.png 中的 4 位数字；queryString 用「编码形态」）
curl -sk -b cj.txt -X POST \
  "https://ismu.shmtu.edu.cn:8443/eportal/InterFace.do?method=login" \
  --data-urlencode "userId=<账号>" \
  --data-urlencode "password=<RSA(reverse(明文 + \">\" + mac))，256 hex>" \
  --data-urlencode "service=%E6%A0%A1%E5%9B%AD%E7%BD%91" \
  --data-urlencode "operatorPwd=" \
  --data-urlencode "operatorUserId=" \
  --data-urlencode "validcode=<4位数字>" \
  --data-urlencode "passwordEncrypt=true" \
  --data-urlencode "queryString=<queryString>"
```

返回含义：

| `message` | 含义 | 处理 |
|---|---|---|
| `验证码错误.` | 验证码为空/错误/已过期 | 重新取图识别后重试 |
| `认证失败` | 验证码已过，账号或密码不对（假账号实测回这个） | 停止重试，提示用户 |
| `用户不存在或者密码错误!` | 账号存在但凭据被拒 —— **多半是密文里的 mac 不对或明文没反转**，与密码本身无关 | 按 §八 逐项核对，别急着改密码 |
| `所在地区不能使用本服务` / 服务不对应 | `service` 不匹配当前接入类型 | 换另一种 `service` 再试 |
| `""` + `result: success` | 登录成功 | 进入成功页 |

## 八、客户端完整流程（现状）

> 2026-09-14 有线网口环境**实机登录成功**。本章是「程序现在实际怎么走」的口径，
> 每步都能在代码里对上；各处该编码几次的细节见 §3.5。

### 8.1 端到端时序

| # | 步骤 | 代码 | 关键点 |
|---|---|---|---|
| 1 | 读配置 / 取凭据 | `program_env_config.get_user_list()`、`credential_provider` | 可选：按**物理网卡 MAC** 向自建凭据服务换账号，换不到回退本地账号 |
| 2 | 联网检测 | `test_net()` → `is_connect_by_sites()` | 只认 2xx + 响应体特征，且要 https 通道交叉验证；结论带短 TTL 缓存 |
| 3 | 抓 queryString | `get_query_string()` → `get_query_string_by_url()` | 并发探测 5 个 **http 明文**地址，等网关劫持跳转；取 `?` 之后整串（编码成表单形态返回） |
| 4 | 建会话 | `EPortalClient.open_entry()` | 用**原始形态**拼 `index.jsp?…`，服务端据此把 wlanuserip / mac 绑到会话 |
| 5 | 取门户配置 | `query_page_info()` | 拿 `validCodeUrl` + RSA 公钥 + `passwordEncrypt`；body 用**原始形态** |
| 6 | 绑定服务 | `query_services()` | `InterFace.do?method=getServices&queryString=`（URL 上用**编码形态**） |
| 7 | 查账号服务 | `query_account_service()` | `userV2.do?method=getServices`，返回值只用来把候选 `service` 排序 |
| 8 | 取验证码 | `fetch_valid_code()` | 服务端**每次 GET 都换新图**，所以重试是真换图 |
| 9 | 识别验证码 | `_obtain_valid_code()` → `captcha_solver` | `ddddocr` 优先，失败交给上层（GUI 弹窗）；识别不出按**可重试**处理 |
| 10 | 提交登录 | `_login_portal_once()` → `submit_login()` | `service` 两个候选依次试；密码 `RSA(reverse(pwd + ">" + mac))` |
| 11 | 结果判定 | `_confirm_login_success()` | 响应含糊时**强制重探**网络复核（`force=True`，不吃缓存） |
| 12 | 兜底 | `_login_h3c()` | 主门户失败再试另一套 `hwifi/portalauth`（目前仅在校园无线环境有意义） |

要点：

- **queryString 是「捡回来的」，不是算出来的**：mac / wlanuserip 都由网关按会话现生成，
  程序只从劫持 URL 里取整串再原样透传（不读网卡 MAC、不缓存上次的值）
- **密码加密的明文必须反转**：`reverse(pwd + ">" + mac)`，漏掉这一步门户解出来是反的密码
- **`service` 不猜**：按 `userV2` 返回值排序后**两个候选都试**（容器/网关代拨下网络类型常判错）

## 十、未决问题

1. **明文密码是否仍被接受**：用假账号无法区分（两种情况都返回"认证失败"）。当前实现
   在 `pageInfo.passwordEncrypt=true` 时一律走 RSA，更稳妥。
2. **验证码是否永久强制**：目前 `pageInfo` 恒返回 `validCodeUrl`。若这是风控临时策略，
   未来可能取消——代码已做兼容（`validCodeUrl` 为空则跳过验证码步骤，见
   `PortalPageInfo.need_valid_code`）。
3. **`hwifi.shmtu.edu.cn/portalauth` 那套流程**：需在校园无线网络环境下再抓一次包确认
   其当前形态。目前仅作为 `_login_eportal` 失败后的兜底保留。
4. **无线 i-SHMU 场景下 `service` 是否总能拿到 `iSMU`**：`userV2` 接口依赖传入的
   queryString 区分网络，本次用 HAR 的两份 queryString 均验证通过；换设备/换 AP 后
   建议保留一份日志观察。
